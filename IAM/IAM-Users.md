# AWS IAM Users (Identity and Access Management)

## 1. Introduction to IAM Users

AWS Identity and Access Management (IAM) is a service that helps securely manage access to AWS resources.

An IAM User is an identity created within an AWS account to represent an individual person or an application that needs to interact with AWS resources.

Each IAM User has its own identity and credentials, allowing AWS to identify who is making a request.

IAM Users can be used for:

- Identifying individual users within an AWS account.
- Providing access to AWS resources.
- Managing individual permissions.
- Authenticating programmatic requests.
- Managing access through passwords and access keys (where supported).

### Real-World Example

Suppose a software company has three developers:

- Frontend Developer
- Backend Developer
- DevOps Engineer

Each developer may require different access to AWS resources.

Instead of sharing the AWS Root Account credentials, individual identities can be created to manage access separately.

For example:

- Frontend Developer: Read access to S3.
- Backend Developer: Upload access to S3.
- DevOps Engineer: Required EC2 management access.

This approach improves security, accountability, and access management.

---

## 2. Understanding IAM User

An IAM User is an identity that belongs to one specific AWS account.

Important characteristics:

- Every IAM User has a unique username within its AWS account.
- An IAM User belongs to only one AWS account.
- Each user can have its own credentials.
- Permissions can be assigned individually.
- Users have no permissions by default.
- Users can access AWS resources only when the required permissions are granted.
- IAM Users are different from the AWS Root User.

### Important Concept

An IAM User is not a separate AWS account.

All IAM Users operate within the AWS account in which they were created.

Any AWS usage and resource costs generated by IAM Users are billed to the associated AWS account.

---

## 3. IAM User vs AWS Root User

The AWS Root User is the original identity created when an AWS account is registered.

It has full access to the AWS account and should be protected carefully.

An IAM User is an additional identity created inside an existing AWS account.

| Feature | Root User | IAM User |
|---------|-----------|-----------|
| Creation | Created with AWS account | Created by an authorized administrator |
| Access | Full account access | Based on assigned permissions |
| Identity | Account owner identity | Individual or workload identity |
| Permissions | Full access | No permissions by default |
| Usage | Account-level administration | Specific access requirements |
| Security | Requires strong protection | Requires controlled permissions |

### Security Recommendations

- Never share Root User credentials.
- Enable MFA on the Root User.
- Avoid using the Root User for daily development.
- Use appropriate identities and permissions for regular operations.

## 4. IAM User Components

An IAM User consists of an identity and associated credentials.

Important components include:

### A. User Name

A username identifies an IAM User within an AWS account.

Example:

```text
backend-developer
frontend-developer
devops-engineer
```

Each username must be unique within its AWS account.

### B. Console Password

A console password allows an IAM User to sign in to the AWS Management Console.

The traditional IAM User workflow supports console access through a username and password.

An IAM User with console access generally needs:

- AWS Account ID or Account Alias.
- IAM Username.
- Console Password.

After successful authentication, the user can access AWS resources according to their assigned permissions.

Important:

Creating an IAM User does not automatically provide console access.

Console access must be enabled separately.

### C. Access Key ID

An Access Key ID is used to identify credentials when making programmatic requests to AWS.

Example format:

```text
AKIAIOSFODNN7EXAMPLE
```

Access Key IDs are commonly used with:

- AWS CLI
- AWS SDKs
- AWS APIs
- Application integrations

### D. Secret Access Key

A Secret Access Key is the secret component associated with an Access Key ID.

It is used to authenticate and sign AWS requests.

Important:

- Never share your Secret Access Key.
- Never upload it to GitHub.
- Never hardcode it into frontend code.
- Store credentials securely.
- Rotate or deactivate long-term access keys when necessary.

The Secret Access Key is shown when the key is created. AWS does not allow you to retrieve the original secret later.

### E. Multi-Factor Authentication (MFA)

MFA adds an additional layer of security to AWS authentication.

Instead of relying only on a password, the user must provide an additional verification factor.

Examples:

- Authenticator applications.
- Security keys.
- Passkeys.
- Supported hardware MFA devices.

MFA helps protect AWS accounts even if passwords are compromised.

## 5. Types of IAM User Access

IAM Users can interact with AWS in different ways depending on their configured credentials.

### A. Console Access

Console access allows users to interact with AWS through the web-based AWS Management Console.

Example:

A developer signs in to AWS and manages EC2 instances through the browser.

Traditional console sign-in requires:

1. AWS Account ID or Alias.
2. IAM Username.
3. Password.

### B. Programmatic Access

Programmatic access allows developers and applications to interact with AWS services using APIs, CLI commands, and SDKs.

Common tools include:

- AWS CLI
- AWS SDK for JavaScript
- AWS SDK for Python
- Other AWS SDKs

Example:

A Node.js application uses the AWS SDK to communicate with AWS services.

Programmatic access using long-term IAM User credentials generally requires:

1. Access Key ID.
2. Secret Access Key.

Temporary credentials may also be used through supported authentication methods.

### Console Access vs Programmatic Access

| Feature | Console Access | Programmatic Access |
|---------|----------------|---------------------|
| Interface | Web Browser | Code, CLI, API |
| Authentication | Username and Password | Credentials or temporary authentication |
| Main Usage | Manual AWS management | Application integration |
| Example | Managing S3 through AWS Console | Uploading files using AWS SDK |

## 6. IAM User Permissions

When an IAM User is created, it has no permissions by default.

This means the user cannot access AWS resources or perform AWS operations unless permissions are granted.

Permissions can be provided through:

1. Policies attached directly to the user.
2. Policies attached to IAM Groups containing the user.
3. Other applicable AWS authorization mechanisms.

### Example

Suppose an IAM User needs to read files from an S3 bucket.

An administrator can attach an appropriate policy.

Example permission:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
```

This policy allows the user to retrieve objects from the specified bucket.

It does not automatically provide permission to upload or delete objects.

### Important

Authentication and Authorization are different concepts.

- Authentication: Verifies who you are.
- Authorization: Determines what you are allowed to do.

A successful login does not mean that the user has access to every AWS service.

## 7. IAM User Identifiers

AWS uses different identifiers to identify IAM Users.

### A. User Name

The human-readable name assigned to an IAM User.

Example:

```text
backend-developer
```

### B. User ID

A unique identifier automatically assigned by AWS when the IAM User is created.

It is different from the username.

### C. ARN (Amazon Resource Name)

An ARN uniquely identifies an AWS resource.

An IAM User ARN generally follows this structure:

```text
arn:aws:iam::ACCOUNT_ID:user/USERNAME
```

Example:

```text
arn:aws:iam::123456789012:user/backend-developer
```

ARN components:

- arn: Identifies the ARN format.
- aws: AWS partition.
- iam: AWS service.
- ACCOUNT_ID: AWS account identifier.
- user: Identifies the IAM resource type.
- USERNAME: IAM User name.

ARNs are commonly used in IAM Policies to identify specific resources and principals.

## 8. Creating an IAM User (Traditional IAM Workflow)

The traditional AWS IAM interface supports creating IAM Users through the IAM Console.

General steps:

1. Sign in to the AWS Management Console.
2. Search for IAM.
3. Open IAM.
4. Navigate to Users.
5. Select Create user.
6. Enter the username.
7. Configure the required access options.
8. Configure console access if needed and supported.
9. Configure permissions.
10. Review the settings.
11. Create the user.

After creation, additional credentials and permissions can be managed through the user's settings.

### Important Note About the New AWS Experience

AWS has introduced a newer experience for account and project management.

In this new experience:

- Human users are invited through the Team page.
- IAM Users cannot be created with console access through the new experience.
- IAM User management remains available through traditional IAM functionality for supported use cases.
- Existing IAM Users and their credentials may continue to work.

Therefore, the absence of a console password option in the new experience does not mean that IAM Users universally support only programmatic access.

The traditional IAM workflow still supports console passwords.

For modern workforce access, AWS recommends IAM Identity Center rather than creating long-term IAM User credentials for human users.

## 9. IAM User Security Best Practices

Security is one of the most important parts of IAM.

Important recommendations:

### 1. Avoid Sharing Credentials

Every person should use their own authorized identity.

Never share passwords or access keys between developers.

### 2. Enable MFA

Enable Multi-Factor Authentication wherever applicable.

MFA provides additional protection against unauthorized access.

### 3. Follow Least Privilege

Give users only the permissions required for their responsibilities.

Avoid unnecessary full access.

### 4. Protect Access Keys

Never expose Access Key IDs and Secret Access Keys in public repositories.

Avoid storing credentials directly inside application source code.

### 5. Rotate Long-Term Access Keys

If a use case requires long-term access keys, manage and rotate them appropriately.

Remove unused or compromised credentials.

### 6. Remove Unused Users

Regularly review IAM Users and disable or delete identities that are no longer required.

### 7. Avoid Using Root Credentials

Do not use Root User credentials for everyday development or application integration.

### 8. Prefer Temporary Credentials

For applications running on AWS services, prefer IAM Roles and temporary credentials instead of permanent IAM User access keys.

## 10. IAM User in Real-World Development

Consider a MERN application that uses AWS services.

The application may require access to:

- Amazon S3 for file storage.
- Amazon EC2 for backend hosting.
- Amazon RDS for relational databases.
- AWS Lambda for serverless functions.

Different people and applications may need different permissions.

IAM helps administrators control these permissions.

### Example: Development Team

| Identity | Required Access |
|----------|-----------------|
| Frontend Developer | Required frontend-related AWS resources |
| Backend Developer | Required backend and storage resources |
| DevOps Engineer | Infrastructure management |
| Administrator | Authorized administrative operations |

Permissions should always be based on actual responsibilities.

For applications hosted on AWS, IAM Roles are generally preferred over IAM User access keys.

---

## 11. IAM User vs IAM Role

IAM Users and IAM Roles are both IAM identities, but their purposes are different.

| Feature | IAM User | IAM Role |
|---------|-----------|-----------|
| Purpose | Individual or workload identity | Assumable identity |
| Credentials | Can have long-term credentials | Provides temporary credentials when assumed |
| Console Password | Supported in traditional IAM | No standard IAM Role login password |
| Access Keys | Can have long-term access keys | Temporary credentials are commonly used |
| Usage | Specific identity access | Applications, services, users and cross-account access |
| Example | Legacy developer identity | EC2 accessing S3 |

AWS recommends IAM Roles and temporary credentials for workloads running on AWS.

## Conclusion

IAM Users are one of the fundamental concepts of AWS Identity and Access Management.

They help identify individual users and workloads within an AWS account and provide controlled access through credentials and permissions.

Understanding IAM Users is important for managing existing AWS environments, understanding legacy infrastructure, and learning how AWS authentication and authorization work.

Although AWS recommends IAM Identity Center for human workforce access and IAM Roles for workloads, understanding IAM Users remains valuable when working with existing AWS environments and specific programmatic use cases.

### Learning Goal

Understand how IAM Users are created, identified, authenticated, authorized, and secured.
